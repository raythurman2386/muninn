# Internationalisation (i18n): survey and proposed approach

Status: investigation for #71, against `main` at `4c89a780` (v0.8.0). This document
records what is English today, what Rune already does, and one recommended way to
extract it. It ships **no** translations and changes **no** user-visible text.

The goal is a single seam for user-visible language, not a locale pack. "Ship a
second language" is a later issue (see [Follow-ups](#8-follow-ups)); so is full RTL
support, which is blocked on a missing Rune capability described below.

## Scope

In scope:

- an inventory of user-visible strings, grouped by crate and surface
- the date/weekday tables, relative-date phrases, and archive-heading behaviour
- what Rune (the pinned rev) does and does not provide for locale, text
  direction, and mirrored layout
- a recommended library, file layout, and test strategy
- an RTL sketch: what flips, what must not, and what Rune cannot do yet

Explicit non-goals (do not churn these):

- on-disk file format: `@{YYYY-MM-DD}`, `@@{HH:mm}`, footer keys and values,
  `kanban-plugin`, `**Complete**`, `## Archive`, tags, wikilinks, frontmatter,
  and paths. i18n is for what Muninn **shows**.
- rewriting an existing board's marker word or date language
- translating developer diagnostics and logs
- adding a locale picker, translated help, RTL layout, or a second catalog

looked up; there is no message catalog, no locale setting, and no locale data.

## 2. Dates, times, and numbers

### 2.1 Month and weekday tables

`crates/muninn-core/src/kanban/dates.rs:4` says it plainly: “There is no
dependency and no locale data: month and weekday names are English, the language
of a new file.”

- `MONTHS` (`dates.rs:39`) is `"January"` … `"December"`.
- `WEEKDAYS` (`dates.rs:54`) is `"Sunday"` … `"Saturday"`, indexed by
  `CivilDate::weekday()`, where Sunday is 0.
- `format_date()` (`dates.rs:214`) and the `date_token` token expander
  (`dates.rs:264`, names at `:273`) use those tables for `MMMM`, `MMM`, `dddd`,
  `ddd`, `dd`. `Do` uses an English ordinal
  (`ordinal`, used at `dates.rs:279`), and `format_time()` uses English
  `AM`/`PM`.
- Reading a written date back for sorting also matches English month names
  (`month_name`, `dates.rs:533`–`542`), so display and parse are coupled today.
- `docs/kanban-format.md:176`–`190` documents the tokens as English and states
  “Month and weekday names are English; Muninn has no locale table.”

### 2.2 Relative dates

`relative_days()` (`crates/muninn-ui/src/kanban_dates.rs:1008`–`1015`) returns:

```
0  => "today"
1  => "tomorrow"
-1 => "yesterday"
n>0 => "in {n} days"
n<0 => "{-n} days ago"
```

It is shown beside a card date when `show-relative-date` is on. Tests pin the
English phrases at `kanban_dates.rs:1094`–`1097`. This is a single function, so
it is one of the cheapest pieces to catalog later.

### 2.3 Filter chips and other date copy

`KanbanFilter::summary()` (`kanban_search.rs:184`–`185`) builds “today” /
“overdue” into the header summary; the filter panel buttons use “Today” /
“Overdue” (`kanban_search.rs:820`–`832`). These are display strings only; the
filter is not persisted. The date-range fields accept only `YYYY-MM-DD`
(`filter_date`), which must stay ASCII.

The date picker adds three locale-sensitive behaviours beyond words:

- weekday initials are hardcoded `S M T W T F S` (`kanban_dates.rs:698`);
- the first column is always Sunday (`first.weekday()`, `kanban_dates.rs:706`);
- the month/year title is `MMMM YYYY` (`kanban_dates.rs:666`).

Week start is a locale convention (Monday in much of Europe, Saturday in parts
of the Middle East), not just a translation. A later locale pack needs a
`first_weekday` value in the date names, not only translated initials.

### 2.4 Display versus file language

This distinction matters more than the translation itself:

- **File writes** happen in `DateSettings::date_token()`/`time_token()`
  (`dates.rs:780`–`800`), `ArchiveSettings::stamp()` (`archive.rs:149`), and
  `link_replacement()` (`kanban_dates.rs:469`). These write the user's
  `date-format`/`time-format` with English month names and ASCII digits.
- **Display** happens at `kanban_dates.rs:958`, `kanban_views.rs:802`, and the
  picker title. These may use a UI locale later.
- **Parsing** accepts English month names (`dates.rs:535`).

Recommendation: keep **file** output English and ASCII even when the UI is
translated. Only display uses translated names. That preserves the precedent
that new file text is English (like `## Archive`) and avoids turning a board's
language into a side effect of the UI language. If a user explicitly writes
`MMMM` in `date-format`, the file still gets the file language, not the display
language. This needs two entry points, not one formatter with an ambient global.

Numbers: counts are plain decimal (`plural()` in `view.rs:4757`,
`trash_bytes()` at `view.rs:3068`), with no grouping and no locale digits.
`YYYY-MM-DD` and `HH:mm` must stay ASCII. Locale digit shaping, grouping, and
plural rules can wait.

## 3. Archive heading behaviour

The archive is a good precedent for “the user's file language wins”:

- A new archive is created with `***` and `## Archive`
  (`ENGLISH_ARCHIVE_WORD`, `crates/muninn-core/src/kanban/archive.rs:40`;
  `append_archive_card`, `archive.rs:389`–`411`).
- Reading recognises a fixed table of eight marker words
  (`ARCHIVE_WORDS`, `crates/muninn-core/src/kanban/parse.rs:29`–`38`), matched
  exactly after `## ` (`archive_word`, `parse.rs:314`–`320`).
- An existing file's word is preserved; only a **new** heading is English.
  This is documented at `docs/kanban-format.md:148`, `:273`–`284`, and
  `README.md:338`.
- Done-lane markers follow the same pattern (`DONE_MARKERS`,
  `parse.rs:19`–`27`).

Implication: do **not** translate `ENGLISH_ARCHIVE_WORD` based on the UI locale,
and do not rewrite an existing heading. The archive page's title
(`kanban_archive.rs:151`) is chrome and may translate; the heading bytes may
not. If a future locale wants a different **new** marker word, that is a
file-format decision with its own issue, not a side effect of UI i18n.

## 4. RTL today

There is no `dir`, `rtl`, `text_direction`, or mirrored-layout handling in the
app crates. `grep -rniE 'rtl|text_direction|mirrored|bidi|direction' crates/`
finds only comments, identifiers (the substring `rtl` occurs in words such as
“partly” and “AutostartLink”), and Unicode-title tests
(`crates/muninn-core/src/vault.rs:2108`), not layout code.

### 4.1 What Rune provides

Evidence is from the checkout for the pinned rev
`b39c24f7fb588defba035113f3cc8431fae15935` (`Cargo.toml:29`), in
`~/.cargo/git/checkouts/rune-c9b805e9ed8a3730/b39c24f/`.

|---|---|---|

| Web export | No `dir` or `lang` attributes emitted. | No `dir=`/`lang=` in `crates/rune/src/runtime/web/export/`. |

Conclusions:

1. Rune does **not** provide a locale catalog, a locale setting, or mirrored
   layout. Those are Muninn's to build.
2. Rune does provide correct bidirectional **shaping**. A pure Arabic or Hebrew
   label will display its glyphs in the right order even though the paragraph
   has no explicit base direction.
3. Rune cannot set a paragraph/base direction or a widget direction. Mixed
   content (Arabic label plus Latin path, Arabic sentence with a date) can pick
   the wrong base direction under `Auto`, and for unwrapped labels `Align::End`
   means the physical right edge, not “end for this direction”.
4. App-level mirroring can be built by Muninn today, but correct RTL text and
   mixed-direction layout are blocked on an upstream Rune capability. File an
   upstream issue for `TextSpec`/`El` base direction (and, ideally, a logical
   `Start`/`End` and row mirroring). Do not fork Rune for it.

## 5. Recommended approach

### 5.1 Decision

Adopt a **small in-crate catalog** in a new `muninn-i18n` crate, with:

- one compile-time-keyed `en-US` catalog (a Rust exhaustive match)
- typed formatting functions for plurals, relative dates, and dates/times
- `&'static str` returns, so existing Rune call sites do not start allocating
  or handling lookup failures
- one seam (`t(Key::…)` and the date/plural helpers) that a future Fluent or
  ICU-backed implementation can satisfy without touching call sites

This slice adds the crate and the seam only. It does **not** convert the UI;
conversion is the follow-up extraction work, area by area.

### 5.2 Why a catalog rather than Fluent now

Fluent and an `en-US.ftl` file are a reasonable end state, but they are the
wrong first step for this repository:

- The immediate gap is **extraction**, not translation. There is one locale and
  no translator workflow yet.
- A typed Rust catalog is compile-checked. Adding `Key::AddCard` without English
  text fails the build; Fluent message IDs are runtime strings and a missing
  message becomes a runtime fallback.
- The workspace deliberately keeps dependencies thin (`muninn-core` has only
  `serde_json`; `ARCHITECTURE.md:19`). Fluent adds `fluent-bundle`, a parser,
  locale negotiation, and resource loading before there is a second locale.
- The handful of grammatical needs (one/many, “in N days”, ordinal dates) fit
  typed functions; Fluent's `select`/plural machinery buys little until a
  language with complex plural rules arrives.
- `t()` is the escape hatch: if translators later need FTL, the catalog
  implementation changes and call sites do not.

Revisit Fluent if/when a locale pack lands and translators want a non-Rust
format. At that point evaluate `fluent-bundle` plus `en-US.ftl` against this
same API. Do not adopt ICU4X for this slice; the `icu_*` entries in `Cargo.lock`
are transitive (Parley/fontique), not a Muninn dependency, and CLDR data is
unnecessary for one locale. Re-evaluate ICU4X when locale-aware month names,
week start, plural rules, or digit grouping are actually needed.

### 5.3 Crate, API, and file layout

```
crates/muninn-i18n/
  Cargo.toml           # no external dependencies in the first slice
  src/lib.rs           # Lang, t(), plural(), relative_day(), date re-exports
  src/key.rs           # Key enum generated by a local keys! macro
  src/en_us.rs         # exhaustive English match: the only copy assertions
  src/dates.rs         # DateNames: months, weekdays, ordinals, AM/PM, week start
  tests/catalog.rs     # key uniqueness, helper behaviour, pseudo-locale checks
```

Sketch:

```rust
// key.rs — a local declarative macro, no proc macro
keys! {
    AddCard        => "kanban.add_card",
    Archive        => "kanban.archive",
    Today          => "date.today",
    // ... one row per user-visible string
}

// lib.rs
pub fn t(key: Key) -> &'static str;              // current UI language
pub fn t_in(lang: Lang, key: Key) -> &'static str;

/// Parameterised copy is a typed function, never a UI-side format!.
pub fn files_skipped(n: usize) -> String;
pub fn relative_day(days: i64) -> String;        // today / tomorrow / in N days
pub fn plural_notes(n: u64) -> String;

// dates.rs
pub struct DateNames {
    pub months: [&'static str; 12],
    pub weekdays: [&'static str; 7],             // Sunday = 0, matching CivilDate
    pub week_start: u8,                          // en-US: 0 (Sunday)
    // ordinal / AM-PM behaviour lives in functions
}
pub const EN_US: DateNames = /* ... */;
```

The English catalog is an exhaustive `match key { … }`, so `cargo check` is the
missing-copy test. `keys!` should also emit a `Key::ALL` slice for duplicate and
coverage tests.

Why `&'static str` matters: current signatures use `&'static str`
(`PaletteAction::label`, `KanbanSection::title`, `KanbanKey.label`), and Rune's
`text()` takes `impl Into<String>`. Keeping static English avoids forcing
lifetime changes through `muninn-core` and avoids a failed lookup at draw time.

### 5.4 Layering

`muninn-i18n` is a leaf data crate: no workspace dependencies. `muninn-core`,
`muninn-ui`, and `muninn-app` may depend on it. Update `allowed_edges()` in
`xtask/src/main.rs:153` in the same change that adds the dependency, as
`ARCHITECTURE.md:298` requires:

```
muninn-core -> muninn-i18n
muninn-graph -> muninn-core, muninn-i18n   (only if graph copy needs it)
muninn-ui   -> muninn-core, muninn-graph, muninn-sync, muninn-i18n
muninn-app  -> ... , muninn-i18n
```

`muninn-core` must not depend on `muninn-ui`; the catalog is data, not UI.
Setting labels stay in `schema.rs` as keys (or move to the catalog and leave
`schema.rs` with key IDs). Do not duplicate them.

### 5.5 Dates and times

Split the formatter into two explicit paths in `muninn-core`:

- `format_date_for_file(date, format)` — English names, ASCII digits; used by
  `date_token`, `time_token`, archive `stamp`, and `link_replacement`.
- `format_date_for_display(date, format, names)` — names from the UI locale;
  used by the card foot, list/table, and picker title.
- Keep `format_date()` as the English/file default until call sites migrate, so
  existing tests and file output do not change.

`DateNames` owns the month/weekday arrays, ordinal rules, AM/PM words, and
`week_start`. `format_date` keeps the token grammar exactly as documented; only
the substitutions change. `parse_date` continues to accept English month names
(file language); a future locale-aware parser is a separate decision.

The date picker reads `DateNames.week_start` instead of hardcoding Sunday, and
its weekday header uses the short names from the table. en-US output is
byte-identical to today, so this slice has no visible change.

Relative dates and plurals become typed helpers (`relative_day`,
`plural_notes`, …), not `format!` in the view. English output stays exactly
“today”, “tomorrow”, “yesterday”, “in 3 days”, “2 days ago”, “1 note”,
“3 notes”.

### 5.6 Migration order (follow-up, not this issue)

1. Add `muninn-i18n` and its tests; no call-site changes.
2. Move `shortcut_groups()` and Help (pure table, easy review).
3. Move command palette labels/hints/keywords/sections.
4. Move settings chrome and the kanban setting labels/help from `schema.rs`.
5. Move Kanban chrome, filters, archive page, and board/graph chrome.
6. Move dynamic status/error messages, keeping internal diagnostics English.
7. Add the lint, then a pseudo-locale pass to find stragglers.
8. Only after extraction is complete, open the “ship a locale pack” issue
   (catalog, locale picker, RTL, translated help/dates).

Each step preserves English output, so review is about the seam, not copy.

### 5.7 Test strategy: pin English copy once

The rule: **English copy is asserted in the catalog, nowhere else.**

- The exhaustive `match` in `en_us.rs` is the copy pin. `cargo check` fails if
  a key has no English text; review diffs are one file.
- `tests/catalog.rs` asserts `Key::ALL` has no duplicates, every key returns
  non-empty text, and no message contains untranslated `{}` placeholders
  (arguments are typed functions).
- Behaviour tests use keys or `t(Key::…)`, never literal sentences. Move the
  existing copy assertions when their area migrates: date names
  (`dates.rs:1370`–`1429`), relative phrases (`kanban_dates.rs:1094`), archive
  marker tests (`kanban/tests.rs:3097`), and tray strings (`tray.rs:326`–`362`).
- UI tests and UI-smoke select widgets by stable Rune key, not by English label.
  `El::key` is already used widely (`key("kanban-settings-close")`,
  `key("recovery-banner")`, `key("palette-items")`). The one remaining
  label-based lookup, `scripts/ui-smoke/single_instance.sh:113`
  (`n.get("label") == "Appearance"`), should become a key lookup; the smoke
  harness already reads keys (`scripts/ui-smoke/board_pixels.py:67`).
- Add `xtask i18n-lint`: fail when `text("…")`, `.label("…")`, `.help("…")`,
  `.placeholder("…")`, or a user-facing `status = "…"` appears outside
  `muninn-i18n`, with an allowlist for keyboard glyphs, symbols, keycaps,
  file-format examples, and paths. This keeps the extraction from regressing
  after the initial sweep. The exact allowlist is an implementation detail of
  that follow-up, not a reason to skip the lint.
- Once `Lang` exists, add a `Lang::Pseudo` catalog (bracketed/expanded English)
  and a test that renders key screens with it: any un-bracketed sentence is a
  hardcoded string. This catches dynamic strings the lint cannot see. Keep
  pseudo output out of release builds.

## 6. RTL sketch

Full RTL is a later issue; this section defines what a future `Dir` would touch.
The app currently has fixed physical order, so a `Dir` must be applied at the
layout layer, not sprinkled through draw code.

### 6.1 What flips

| Surface | Change in RTL | Where |
|---|---|---|
| Root layout | sidebar moves from leading (left) to trailing (right); the divider follows; main column takes the other side | `view.rs:21` `view()` |
| Note rail | links rail moves from the right edge to the left; the `>= 980.0` width rule stays | `view.rs` `main_body()` (`:2156`) |
| Top bar | toolbar/icon order mirrors; back/forward chevrons `‹`/`›` swap glyphs; title/path text aligns to the right | `view.rs:3553` `topbar()` |
| Sidebar | counts and expand/collapse affordances swap sides; note-row padding mirrors | `view.rs:84` `sidebar()` |
| Menus | menu label and item text align right; submenu/arrow affordances mirror | `view.rs:1605` `context_menu()` |
| Status/recovery banners | action buttons swap sides; text aligns to the right | `view.rs:3464` |
| Kanban lane row | first lane sits at the right; subsequent lanes go left; logical lane index 0 stays the first lane heading | `kanban_view.rs`, `kanban_lanes.rs` |
| Kanban card | checkbox/mark moves to the right of the card text; tag chips and metadata mirror | `kanban_view.rs` card row |
| Kanban header/toolbar | search/filter/view/settings button order mirrors; horizontal scroll and its scrollbar side need review | `kanban_view.rs:623` onward |
| List/Table views | table columns flip (Lane at right, Progress at left); card rows mirror; horizontal scrolling starts from the right | `kanban_views.rs:514` |
| Date picker | weekday columns run right-to-left; `week_start` still decides the first column; month arrows swap | `kanban_dates.rs:666`–`800` |
| Dialogs | close button moves to the left; primary/secondary button order mirrors; field labels align right | `view.rs:915` settings, confirm rows |
| Directional glyphs | `‹`/`›`, `↳`, `→`, `↑`/`↓` hints need mirroring or rewriting per direction | `view.rs:3829`, `:3840`, `:2260`, `:2586` |

### 6.2 What must not flip

- **The Markdown file.** Bytes, line order, indentation, list markers, heading
  levels, and frontmatter are data. RTL is display only.
- **Wikilink syntax.** `[[Note]]`, `[[Note#Heading]]`, `[[Note|alias]]`,
  `![[embed]]` stay LTR characters. The renderer must not mirror brackets or
  reverse path segments.
- **File-format tokens and ASCII digits.** `@{2026-11-12}`, `@@{14:30}`,
  `date-format`/`time-format` strings, footer keys/values, `kanban-plugin`,
  tags, and code fences stay exactly as written. Do not write Arabic-Indic
  digits or mirrored braces.
- **Markdown table alignment.** `:---`, `---:`, `:---:` are file semantics, not
  UI direction. A right-aligned column stays right-aligned in the file even in
  an RTL UI; if the preview mirrors it, that is a rendering decision inside
  Rune-kit, not a rewrite.
- **Code blocks and inline code.** Always LTR.
- **Keyboard chords and keycaps.** `⌘K`, `Ctrl+K`, `⌘5` do not mirror. The
  *descriptions* (“Move the selection across lanes”) may need arrow wording
  review, but the chord does not.
- **Paths and vault-relative names.** Always logical LTR.
- **Excalidraw board coordinates and graph positions.** The board canvas is
  user-authored geometry; flipping it would change what the user drew. Flip the
  toolbar, not the canvas. Graph node positions likewise.
- **The archive heading and marker words.** File data; see §3.
- **Search text and tag names.** User content, not UI direction.

### 6.3 What Rune cannot do yet

Rune gives correct bidi shaping but no explicit base direction and no mirrored
layout (see §4.1). Consequences:

- A pure RTL label renders in the right glyph order, but it is still placed at
  the physical left edge of its box and `Align::Start` still means left.
- Mixed strings can infer the wrong paragraph direction, and there is no API to
  say “this paragraph is RTL”.
- There is no row-reverse container, so the app must build mirrored rows itself.
- AccessKit receives the label but no direction metadata.

Therefore the first RTL slice should be app-level and limited to:

1. a `Dir` value derived from the chosen locale
2. mirrored root/sidebar/rail/toolbar/table/lane order
3. mirrored directional glyphs
4. `Align::End` used for RTL text blocks where the app controls alignment
5. a call to `rune::text::set_language(Some(tag))` so CJK fallback matches the
   chosen locale (no effect on en-US output)

Full RTL text inside Markdown preview, mixed-direction labels, and correct
per-paragraph alignment need an upstream Rune change. Until then, do not claim
RTL support; document the limitation. A temporary RLM (`U+200F`) prefix is a
possible stopgap for individual labels but should not be spread through the
codebase as a substitute for a base-direction API.

## 7. Non-goals and deferred work

### 7.1 File-format compatibility (explicit non-goal to churn)

Do not change, translate, or normalise:

- `@{YYYY-MM-DD}` / `@@{HH:mm}` tokens and the `@`/`@@` triggers
- `date-format`, `time-format`, `date-display-format` token grammar
- footer keys (`date-trigger`, `show-relative-date`, `archive-with-date`, …)
  and their values (`start`/`end`, `enter`/`shift+enter`, …)
- `kanban-plugin` and frontmatter values
- `**Complete**` and the other `DONE_MARKERS`
- `## Archive` and the other `ARCHIVE_WORDS`, or an existing file's word
- wikilink, tag, heading, block-id, and path syntax
- new-file language: month/weekday names and marker words remain English

A future “file language” feature (for example writing German month names because
the vault is German) is a separate format decision and must not ride along with
UI translation.

### 7.2 Ship translations (later issue)

Not in this slice:

- a second catalog or locale pack
- a locale picker / OS locale detection
- translated Help, settings, palette, Kanban chrome, tray, or errors
- translated month/weekday tables in **files**
- locale week start, plural rules, number grouping, digit shaping
- RTL layout
- translated UI-smoke expectations

Those need their own issue after this approach is accepted. The value of this
survey is that they become mechanical: one catalog to fill, one lint to keep
call sites honest, one date seam, and a known Rune gap for RTL.
